# 2026-10-08: Leech on Linux and Windows, cleanly

For the next agent. Leech runs on Linux only (Chromium 154.0.8037.57 build, Wayland and X11). This plan makes the
same repo carry Windows too, built under the clean-project rules ([conventions.md](../conventions.md), ADR 0001):
what differs by platform lives in one named place per component, every claim about the Windows build has an
oracle before the code exists, and Linux draws exactly what it drew before at every step. Read the conventions,
the newest hand-off, [the release plan](2026-10-01-release.md) and this plan first. Commit and push per finished
step (allowed in this repo), never with AI attribution, and only when `npm run check` and
`npm run check:ui -- --chromium` both exit 0.

**Not a rewrite.** `ui/` and almost all of `chromium/leech/` are portable already (aura, clipboard, file chooser,
`platform_util`, OSCrypt, the shield, sleep, peek, the sandbox profiles). Rewriting them would throw away checked
behaviour for nothing. The work is: isolate the few Linux-only spots, add their Windows side next to them, and
verify both.

Marks: **[checked]** was looked at in the source or the build; **[to check]** is expected but nobody has verified it.

## Result: what works afterwards

- One `ui/` and one `chromium/leech/` build for `target_os = "linux"` and `"win"`. Platform code exists only in
  `chromium/leech/platform/`, `ui/platform/`, `chromium/patches/windows.patch` and `tools/windows-check*`, and
  `npm run check` fails on platform switches anywhere else.
- Linux: unchanged in behaviour and pixels; `check:ui` green; the release tarball as in the release plan.
- Windows: a per-user installer built on Linux installs Leech in the Windows 11 VM; the UI draws from the binary;
  tabs, the page script, downloads, passwords and "Make default" work; the window moves, maximises, snaps and
  closes from the UI. `npm run check:windows` shows it, with numbers recorded in the verification plan.

## What it costs

- A second Chromium target: Windows dependencies in the checkout (several GB, **[to check]**), a packaged
  Windows SDK, `out/Win` (the Linux release build is 9.9 GB). 281 GB were free on 2026-10-08. **[checked]**
- A full Windows release build per release; the Linux one took 4 h 20 min at `-j 5`. **[to check]**
- Windows is only ever seen in the VM ("Wreath Windows 11 frontend", no GPU): software compositing, no hardware
  video. GPU and video problems on real Windows hardware stay unseen until reported.
- Every Chromium update and C++ change builds for both targets. Unsigned installers get a SmartScreen warning.
  DRM on Windows may be capped (step 9).

## Decisions for the owner, before step 1

1. **Install form.** Recommended: Chromium's per-user `mini_installer.exe` (no admin, Start menu, uninstall,
   registry entries for "Make default"). A portable zip can't be the default browser.
2. **Code signing.** Recommended: none for the first Windows release, the README says so. Later: SignPath's open
   source plan or a paid certificate.
3. **Font.** `ui/styles/tokens.css` asks for `Inter Variable`, which this machine has installed; Windows falls back
   to Segoe UI with other metrics. Recommended: ship Inter (OFL) as `woff2` in `ui/` for both. **[checked: no
   `@font-face` in `ui/`]**
4. **Architectures.** x64 only.

## Steps, in order

Each step leaves Linux working and is one or more commits. Resource rules from the conventions hold: builds at a
third of the cores (`-j 5`), lowest priority, steps that write many GB announced to the owner first.

### 0. Room in the documents

- Move the finished plans (each one's own "Done" lines decide) into `docs/plans/done/` and the hand-offs into
  month folders; fix links; `docs/README.md` indexes the new folders. Hand-offs are history: moved, not edited.
- ADR `decisions/platform/0014-windows-as-second-target.md` (proposed): Windows cross-compiled from Linux.
  Options: a Windows build machine, cross-compiling (`docs/win_cross.md` in the checkout), the Electron shell on
  Windows (rejected for the same reason as on Linux: Google sign-in is blocked there).
- ADR `decisions/platform/0015-platform-layer.md` (proposed): where platform code lives (the folders in "Result")
  and that nothing else switches on the platform.
- Done when: `npm run check` passes, no Markdown folder holds more than 8 files, every moved link resolves.

### 1. The verification plan, before any code

`docs/verification/platform.md`, indexed in `verification.md`. Claims, each with an oracle that shares no code
with Leech:

| Claim | Oracle | Method | Threshold |
| --- | --- | --- | --- |
| `ui/platform/paths.js` splits, names and shortens every path as the platform does | Node's `path.win32` and `path.posix` | differential unit test over a generated corpus: drive letters, UNC `\\server\share`, both separators, trailing separators, spaces, umlauts, CJK, emoji, 300-character paths | 100 % agree |
| A file Windows wrote under any corpus name shows in the Downloads panel under its name and folder, and opens | Windows itself: `Get-ChildItem` in the VM | `check:windows` downloads files with those names | 100 % listed, opened |
| A name that isn't valid UTF-16 (a lone surrogate) is reported, not garbled | the corpus entry made for it | same | shown as unreadable, logged with the path |
| A point in the window moves it iff it lies in a caption area the UI reported and in no island | Windows: the window's position from `GetWindowRect` before and after a real drag | `check:windows` drags from a grid of points | 100 % of grid points |
| The maximise button answers `HTMAXBUTTON` | Windows 11 shows the snap layout flyout on hover | screenshot, judged by a person | seen once per release |
| Installing touches only Leech's names in the registry and `%LOCALAPPDATA%\Leech`, also with Chromium beside it | `reg export` of HKCU before and after | registry diff in `check:windows` | zero keys outside Leech's |
| Linux draws exactly what it drew before each step | the build before the step | pixel comparison after the same keys and clicks (conventions) | 0 differing pixels |

Known gaps it names: GPU and hardware video on Windows (no GPU in the VM), DRM playback, high-DPI beyond the
VM's 100 % and 150 %.

### 2. The platform layer on Linux alone

Isolation first, while only Linux builds, so every move is checked against the old pixels.

- `chromium/leech/files/leech_paths.{h,cc}`: `PathToUI(const base::FilePath&)` and `PathFromUI(std::string_view)`,
  the only places a path becomes a UI string or back (`AsUTF8Unsafe`, `FromUTF8Unsafe`). The eight sites in the
  table call them. A path that doesn't convert cleanly is logged with its location, never passed on silently.
- `chromium/leech/platform/`: `leech_platform.h` declares what differs (`PlatformName()`,
  `ClaimDefaultBrowser()`); `leech_platform_linux.cc` holds today's `xdg-mime` code. `leech_default_browser.*`
  shrinks to the shared `DefaultBrowserWorker` part and moves in. The `BUILD.gn` hunk in `leech.patch` lists the
  Linux file under `if (is_linux)`.
- `ui/platform/`: `index.js` (entry, wiring only, reads `info.platform`), `paths.js` (separators, file and folder
  names, home shortening). `downloads.js` and `landed.js` use it. `test/platform-paths.test.mjs` is the
  differential test from step 1.
- Enforcement in `tools/structure.mjs`, with a test in `test/structure.test.mjs`: `BUILDFLAG(IS_` only in
  `chromium/leech/platform/`; `info.platform` read only in `ui/platform/`. The conventions say so.
- Done when: `npm run check`, `check:ui` and `check:ui -- --chromium` pass, Linux pixel-identical, the paths test
  passes at 100 %.

### 3. The toolchain

- In the VM: Visual Studio 2022 Build Tools ("Desktop development with C++"), the Windows SDK version
  `build/vs_toolchain.py` asks for, its Debugging Tools; then
  `python depot_tools/win_toolchain/package_from_installed.py 2022 -w <sdk>` packs a zip. **[checked in the doc]**
- On Linux: `target_os = ['win']` in `leech-chromium/.gclient`, the zip's folder in
  `DEPOT_TOOLS_WIN_TOOLCHAIN_BASE_URL`, `GYP_MSVS_HASH_<hash>` from `gclient sync`'s output, both in
  `leech-chromium/win-env.sh` beside `sync.sh`, outside the repo (Microsoft's files aren't redistributed).
- `chromium/args-win.gn` = `args-release.gn` + `target_os = "win"`, `target_cpu = "x64"`. Static release build
  only: daily work stays on the Linux component build.
- Cross builds stub out `.asm`, so Crashpad can't report on Windows; nothing is uploaded anyway. **[checked in the doc]**
- Done when: `gn gen out/Win` succeeds. Announce the sync's size and the build's hours before running them.

### 4. Leech compiles for Windows

- `chromium/leech/platform/leech_platform_win.cc`: `PlatformName()` is `"win"`; `ClaimDefaultBrowser()` does
  nothing, since on Windows 10/11 Chromium's worker opens the Settings app's Default apps page.
- The `BUILD.gn` hunk lists it under `if (is_win)`.
- `autoninja -C out/Win chrome` lists what's left; the table above is the known part, not necessarily all.
  Whatever else turns up goes behind `platform/` or `leech_paths`, never as an `#if` in place.
- Done when: `out/Win/chrome.exe` links, and Linux as in step 2.

### 5. Leech's identity on Windows

- `chromium/patches/windows.patch` (one patch per subject), Windows-only files: `chrome/install_static/
  chromium_install_modes.{h,cc}` (`kProductPathName` "Leech", `base_app_name`, `base_app_id`, ProgID prefixes
  "LeechHTM" and "LeechPDF", fresh GUIDs from `uuidgen` for `toast_activator_clsid` and `elevator_clsid`), the
  `.ico` from `assets/leech-light.png` in `chrome/app/theme/chromium/win/`. **[checked: the constants exist; the
  complete list to check]**
- The profile then lives in `%LOCALAPPDATA%\Leech\User Data`, the counterpart of `~/.local/share/leech/chromium`.
- `chromium/README.md` lists `args-win.gn` and `windows.patch`, and how the patches apply.
- Done when: the registry claim of step 1 holds in the VM.

### 6. The UI inside the binary

- ADR `decisions/platform/0016-ui-in-the-binary.md`: the `ponytail:` in `UIFolder()` named grit as the upgrade
  once Leech ships as one file; the Windows installer lays files out beside `chrome.dll` and doesn't pack folders
  recursively, so that time is now. **[checked: `create_installer_archive.py` globs one level]**
- A `.grd` generated at build time from the files in `ui/` (generated, so it isn't checked in or hand-kept);
  `chrome://leech` and the page script (`GuestScript::Load`) read from the resources. `LEECH_UI_DIR` stays as the
  development override on both platforms. `tools/stage.mjs` stops copying `leech-ui/`.
- Done when: the staged Linux tree and the Windows install draw the UI with no `leech-ui/` anywhere,
  `page-script` passes, Linux pixel-identical.

### 7. The window caption on Windows

The largest unknown. Linux leaves the frame to the window system; on Windows Chromium draws its own title bar,
sized by the tab strip, which in Leech takes no room.

- Spike, no code: install the step 5 build in the VM, look at both themes. Can the window be moved, resized at its
  edges, snapped with Win+arrows; what shows where Chromium's caption buttons would be. The result goes to
  `docs/spikes/2026-10-XX-windows-caption.md` (a new folder; failures are written down too).
- ADR `decisions/platform/0017-windows-caption.md` from the spike. Expected decision: the UI draws minimise,
  maximise and close on Windows only, and says which of its parts move the window.
- `ui/platform/caption.js`: the buttons (ADR 0002: greys, no borders; the strip's right or the sidebar's top),
  using the existing `L.window('minimize' | 'maximize' | 'close')` calls, which `LeechHandler::Window` already
  serves. The caption areas travel as a new `caption` list in the existing `stage` message beside `islands`
  (`ui/native.js` `watchStage`, `LeechView::SetStage`); Linux sends none.
- `chromium/leech/platform/leech_caption_win.cc` answers the frame's hit test from those areas (`HTCAPTION`;
  `HTMAXBUTTON` on the maximise button), through one hook in `windows.patch` (candidates:
  `BrowserView::IsPositionInWindowCaption`, `BrowserFrameViewWin::NonClientHitTest`, **[to check]**).
- Check that Alt alone and F10, which focus Chromium's hidden app menu on Windows, don't swallow the keyboard.
  **[to check]**
- Done when: the caption claim of step 1 holds at 100 % of grid points, the snap flyout seen once, Linux
  pixel-identical.

### 8. Installer and the Windows check

- `autoninja -C out/Win mini_installer`; nothing to add to `chrome.release` once the UI is in the binary.
  **[to check]**
- `tools/windows-check.mjs` with `tools/windows-check/` beside it (as `ui-check`), run by `npm run
  check:windows`, a long task: takes a given `mini_installer.exe`, puts it on an ISO for the VM, installs and
  starts it as user `Wreath` through a scheduled task, runs the step 1 claims over the DevTools protocol, brings
  back a report and screenshots through the guest agent, restores the VM. Model: vault's `artifacts/vm/run.sh`.
  Never Rewa's `start.sh`: it opens a window on the owner's screen.
- Reaching the guest's DevTools port needs a port proxy in the guest (`netsh interface portproxy`); Chromium
  listens on 127.0.0.1 only. **[to check]**
- Done when: one command prints pass/fail per claim with the counts, and `platform.md` holds the measured numbers.

### 9. DRM, release and documents

- Widevine: `enable_widevine_cdm_component` is on for Windows (`third_party/widevine/cdm/widevine.gni`), so the
  component updater should fetch the CDM. **[checked in the .gni; the download to check]** Many services require
  Widevine host verification on Windows, which needs signing certificates an unbranded build doesn't have. Expect
  Netflix, Prime Video and Disney+ to refuse or stay at low resolution. **[to check]** The README says what plays.
- Release: `leech-<version>-windows-x64-setup.exe` and its sha256 beside the Linux tarball in the same GitHub
  Release, on the owner's go. A winget manifest only after a few releases.
- Documents in the same commits as the code they describe: README (platforms, Windows install, SmartScreen,
  DRM), `package.json` description without "for Linux", roadmap (a Windows phase), `architecture/overview.md`
  (the platform layer), `chromium/README.md`, `tools/README.md`, `verification.md`, the conventions (entries
  list gains `ui/platform/index.js`; the platform rule). A dated hand-off at the end of every session.
- Done when: the release plan's release check passes on Linux, `check:windows` passes, the ADRs are accepted.

## Not in this plan

macOS, arm64 Windows, an own updater (decided against for Linux, same here), Windows-only features (jump lists,
taskbar thumbnails, Mica), CI builds (a Chromium build doesn't fit GitHub's hosted runners), the Electron shell
on Windows (it stays a Linux development shell).
